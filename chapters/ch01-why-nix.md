# 第 1 章 软件部署的问题——为什么需要 Nix

> **本章导读**：在接触任何 Nix 概念之前，我们先要弄清楚 Nix 到底在解决什么问题。本章通过几个每个开发者都经历过的真实场景，剖析传统软件部署模型的根本缺陷——全局可变状态、隐式依赖、破坏性升级——并给出 Nix 的核心承诺。理解了「为什么」，后面十几章的「怎么做」才会顺理成章。

## 1.1 星期一早晨的生产事故

假设你是一名后端工程师。星期五下班前，一切正常。星期一早晨，运维同事打来电话：生产环境的 API 服务挂了。你登上去排查，发现日志里全是这样的错误：

```
ImportError: libssl.so.1.0.0: cannot open shared object file
```

你花了两个小时复盘，最后拼出了完整的事故链：

1. 星期六凌晨，运维响应安全通告，执行了 `apt upgrade`，OpenSSL 从 1.0 升到了 1.1；
2. 系统目录里的 `libssl.so.1.0.0` 被**删除**了；
3. 你们两年前编译部署的 Python 扩展模块，链接的正是这个文件；
4. 服务一重启，动态链接器找不到库，进程起不来了。

注意这个故事里最令人不安的一点：**没有任何人做错任何事**。运维执行升级是安全规范要求的；开发者两年前按当时的最佳实践编译部署；Debian 的包管理器 `apt` 也精确地完成了它的工作——「把系统更新到新版本」。问题不在任何单点，而在整个模型的假设上。

## 1.2 传统部署模型的隐含假设

主流操作系统继承自 1960-70 年代 Unix 的设计：软件被安装到一个**全局共享、可变**的命名空间里。在 Linux 发行版上，这个命名空间就是根文件系统：

```
/usr/bin          所有可执行文件混在一起
/usr/lib          所有共享库混在一起
/etc              所有配置文件混在一起
```

这个模型有一个隐藏的、几乎从不被明说的前提：**系统中同一时刻只存在每个软件「一个版本」，且版本切换是全局的、破坏性的**。

由此衍生出一连串问题。下面这个清单，正是 Nix 作者 Eelco Dolstra 在其 2006 年博士论文《The Purely Functional Software Deployment Model》（纯函数式软件部署模型）中系统分析的「软件部署问题」。我们逐条来看。

### 1.2.1 问题一：不能共存的多版本

你需要同时运行两个项目：老项目依赖 Python 2.7 与 Django 1.8，新项目需要 Python 3.12 与 Django 5。在传统模型下，`/usr/bin/python` 只能指向一个版本。于是社区发明了层出不穷的补丁方案：`python2`/`python3` 双二进制、`update-alternatives`、模块版本管理器（`pyenv`、`nvm`、`rbenv`、`sdkman`……几乎每个语言生态都重新发明了一遍）。

这些工具的共同思路是：把「全局唯一版本」改造成「每用户、每 shell 会话一个版本」。它们能缓解，但底层冲突没有消失——两个项目各自的**传递依赖**（比如一个 C 扩展库链接的 OpenSSL）依然共享系统全局副本，依然可能踩到 1.1 节的事故。

### 1.2.2 问题二：隐式依赖，配置漂移

一台运行了三年的服务器，「它到底装了什么、依赖什么」这个问题几乎无法精确回答：

- 哪些文件是 `apt` 装的？哪些是某年某月有人 `make install` 手动装进去的？
- `/etc` 里的配置被谁改过？改了什么？为什么改？
- 两年前为了调试装的 `strace` 和临时改的 `sysctl` 参数还在吗？

业内把这称作「配置漂移」（configuration drift）：机器的实际状态与任何文档、任何仓库都不一致，且只会越漂越远。于是出现了「雪花服务器」——独一无二、无法重建、没人敢碰的服务器。灾难恢复的真正成本不是恢复数据，而是**回忆出这台机器的完整状态**。

### 1.2.3 问题三：破坏性升级与回滚困难

传统包管理器的升级是**原地替换**：新文件覆盖旧文件，旧版本随即从系统中消失。如果新版本有问题，你只能寄希望于发行版的回滚机制（多数不存在或不完整），或再次升级到一个修复版。在 1.1 节的事故里，「回滚」意味着把 OpenSSL 降回去——而这可能破坏依赖新版本的其他软件。**全局可变状态使得任何变更都无法原子化**。

### 1.2.4 问题四：构建不可复现

你拿到一份五年前的源代码，想在今天的机器上重新构建出一模一样的二进制。通常你会失败：

- 编译器版本变了（今天系统的 GCC 和当年不同）；
- 依赖库版本变了；
- 构建脚本从网络下载的第三方包地址失效或内容变了；
- 构建产物里嵌入了构建时间、随机路径等环境噪声。

而「同输入必同输出」恰恰是安全审计、灾难恢复、长期归档的基石。传统模型对构建的**输入**没有完整记录：编译时的 `/usr/include` 里是什么，取决于那台机器当时的全部历史。

### 1.2.5 问题五：卸载不干净，升级留残渣

`make install` 散落的文件没有清单可循；包管理器的卸载会留下改过的配置、新生成的缓存与状态目录。系统用得越久，残渣越多——这是「重装解决一切问题」这句民间智慧的技术根源。

### 1.2.6 问题六：依赖地狱的国际化版本

同一个问题在应用层的化身：Python 的 `requirements.txt` 不锁传递依赖哈希；Node 的 `node_modules` 锁了但换台机器行为不同；Docker 镜像 «works on my machine» 的最终形态——镜像本身就是一个不透明的二进制黑盒，没人能说清里面每一层是怎么来的（除非每一层都由可复现的构建产出，而这又绕回了问题四）。

## 1.3 一副眼镜：把「安装」看作函数调用

在展开 Nix 的答案之前，请先换上另一副眼镜看软件部署。

一次软件安装，本质上可以抽象为一个函数调用：

```
install(源代码, 编译器, 依赖库, 构建脚本, 构建参数) → 安装好的软件
```

传统模型的问题，全部源于这个函数**不纯**（impure）：

- 它读取了参数之外的环境（系统全局的 `/usr/lib`、`$PATH` 里第一个出现的工具、当前时间、网络状态）；
- 它**破坏性修改**了全局状态（覆盖 `/usr/bin` 里的文件）；
- 同样的输入，两次调用可能得到不同结果（问题四）。

而我们知道，函数式编程对于「不纯的函数」有一整套成熟的治理思想：**让函数变纯——把所有输入显式声明为参数，把所有输出显式作为返回值，禁止副作用**。若能做到，那么：

- 相同输入必然得到相同输出（可复现，解决问题四）；
- 每次调用产生新的返回值，不修改任何已有值（不可变安装，解决问题二、三）；
- 返回值可以被无限次引用而无互相干扰（多版本共存，解决问题一）；
- 「系统状态」就是这些返回值引用的集合，本身就是完整清单（解决问题五、六）。

**Nix 的全部设计，就是把这套纯函数式思想贯彻到操作系统软件部署的每一层。**「包管理器」这个称呼其实低估了它：Nix 是一个「构建与部署的函数式运行时」。

## 1.4 Nix 的五个承诺

基于上述模型，Nix 向用户做出了五个具体承诺。本书余下部分将逐一兑现并深入它们：

1. **多版本任意共存**。每个包的每个版本、每种构建参数组合，都住在自己的目录里，互不可见。你可以同时使用 Python 2.7 和 3.12、OpenSSL 1.0 和 3.x，甚至同一个库的两种编译 flag 组合。
2. **原子升级与回滚**。安装和升级是「构造一个新环境，然后切换一个符号链接」，中间状态不存在。回滚就是把链接切回去，永远是安全的。1.1 节的事故在 NixOS 上表现为：开机菜单里选上一个「系统代」（generation），两分钟内恢复。
3. **完全的依赖追踪**。每个构建产物通过密码学哈希精确声明并记录它引用的所有依赖，运行时所需的一切构成「闭包」（closure），可以被整体复制到任何机器上运行（参见第 17 章）。
4. **可复现的构建与部署**。构建的输入（源码、工具链、依赖、参数）全部显式化并参与哈希计算；锁定输入，即可在任何时间、任何机器上得到一致的产物。整台机器可以由一份声明式配置完全确定（NixOS）。
5. **无特权、无冲突的包操作**。普通用户可以安装自己的包集合，不影响系统与他人——因为一切操作只是在自己的目录里创建新文件，从不修改共享状态。

作为代价，Nix 要求你学习一门小语言（第 6-12 章），接受 `/nix/store` 这个「奇怪」的顶层目录，以及一块经常吃紧的磁盘空间（第 19 章教你怎么治理）。这是一次性的学习成本，换来的是上述五项长期收益。

## 1.5 Nix 与其他方案的边界

| 方案 | 解决了什么 | 没解决什么 |
|------|-----------|-----------|
| 语言级虚拟环境（venv、nvm 等） | 单语言内的版本隔离 | 跨语言依赖、系统库、构建工具链仍是全局的 |
| 容器（Docker） | 运行时隔离与交付一致性 | 镜像本身如何可复现地构建？镜像内仍是传统发行版 |
| 配置管理（Ansible 等） | 期望状态的收敛 | 「收敛」靠反复执行命令逼近，非构造性；包仍是全局可变的 |
| 虚拟机快照 | 整机回滚 | 粒度太粗、体积巨大、无法组合与审计 |
| GNU Guix | 与 Nix 同源思想（见第 3 章） | 生态规模与 NixOS 社区不同；两者互为参照 |

值得注意的是，这些方案与 Nix 并不对立：Nix 可以构建 Docker 镜像（`dockerTools`，第 35 章）、可以生成 Ansible 管理的主机、可以在 CI 中供给可复现环境。Nix 处理的是它们共同的下层问题：**软件究竟是如何被构建与组合的**。

全书分为六个部分：

- **第二部分（第 6-12 章）**：Nix 语言——从值与表达式到惰性求值与惯用法，为读懂一切配置打地基。

- **第四部分（第 22-31 章）**：NixOS——从包到操作系统的完整机制：模块系统、激活、系统切换、启动流程、systemd 集成、状态哲学与部署。

## 1.7 本章小结

- 传统部署模型的根本缺陷是**全局可变共享状态**：单版本假设、破坏性升级、隐式依赖、配置漂移。
- 生产事故（如 OpenSSL 升级导致旧程序无法启动）不是任何人的失误，而是模型的必然产物。
- 把「安装」抽象为函数调用后，问题的本质是该函数**不纯**；Nix 的答案是让部署彻底纯函数化。
- Nix 的五个承诺：多版本共存、原子升级回滚、完整依赖闭包、可复现构建、无特权包操作。
- Nix 与 venv/Docker/Ansible 不在同一层解决问题；它是它们的下层基础设施。
