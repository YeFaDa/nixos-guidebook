# 第 2 章 Nix 的诞生——Dolstra 论文与乌得勒支

> **本章导读**：每一项技术的设计都是对特定问题的回应。本章回到 2003 年的荷兰乌得勒支大学，讲述 Nix 如何从程序变换工具链的构建之痛中萌芽，如何经 Eelco Dolstra 的博士论文获得完整的理论形态，又如何从一篇论文长成一个覆盖整个操作系统的项目。理解这段历史，能解释 Nix身上许多「与众不同」的设计决定。

## 2.1 起点：一台构建服务器的烦恼

故事要从乌得勒支大学（Utrecht University）的软件工程研究组说起。这个小组由 Eelco Visser 领导，研究方向是程序变换与领域特定语言，其旗舰成果是程序变换工具链 **Stratego/XT**。

Stratego/XT 是一个典型的学术软件工程难题：

- 它由几十个相互依赖的工具组成，工具之间用 ATerm 数据格式交换语法树；
- 它持续演进，每天都有新的构建与测试；
- 它需要在多台机器、多个用户环境下构建运行；
- 用户（其他研究者、学生）经常需要旧版本与新版本并存——论文实验要复现，就必须用当初那个版本的工具链。

研究组维护着一台集中构建服务器。围绕这台服务器，Visser 的学生们踩遍了第 1 章列出的所有坑：升级编译器搞坏构建、不同版本的 ATerm 库冲突、清理旧版本导致旧实验无法复现……这些来自真实项目的疼痛，成为后来 Nix 设计的需求清单。Dolstra 论文的致谢与引言里能清楚看到这条脉络：Nix 从第一天起就不是为了「造一个更好的 apt」，而是为了**让持续演进的软件系统可以被可靠地构建、部署和复现**。

## 2.2 Eelco Dolstra 与 2003-2004 年的第一批论文

**Eelco Dolstra**（1981 年生）2001 年进入乌得勒支大学攻读硕士，2003 年开始在同一学校攻读博士（导师 Eelco Visser 与 Arjen de Vries），博士课题正是「软件部署的纯函数式模型」。Nix 这个名字据 Dolstra 本人解释，来自荷兰语-family 词汇里的巧思——「Nix」在荷兰俚语中意为「什么都没有」（niks），对一个以「无副作用」为最高教义的系统来说再合适不过。

关键的早期论文有三篇，构成一条清晰的思想演进线：

1. **2003-2004 年**，Dolstra 与 Visser、de Jonge 发表 *Imposing a Memory Management Discipline on Software Deployment*（ICSE 2004 收录相关工作）。这篇论文做了核心抽象：**软件部署 = 内存管理问题**。传统部署之所以失控，是因为「包」这些对象被随意地「改写」（升级即覆盖）而没有任何「回收纪律」。论文提出把存储管理中的经典概念——不可变性、引用追踪、垃圾回收、按内容寻址——搬到软件部署领域。这是 Nix 全部机制的哲学源头：store 是堆（heap），包是堆对象，依赖是指针，垃圾回收器负责清理不再被引用的包。
2. **2004-2006 年**，围绕 Nix 原型系统的系列论文（如 *Nix: A Safe and Policy-Free System for Software Deployment* 与安全共享相关文章）给出了具体设计：store 路径哈希、派生（derivation）、闭包。第 13-17 章将逐个解剖这些概念，你会发现它们与早期论文中的设计惊人一致——二十年没有根本变动。
3. **2006 年**，博士论文《The Purely Functional Software Deployment Model》定稿，系统整合了上述全部工作：形式模型、Nix 语言、安全性分析、应用案例（包括在真实工具链上的评估）。这篇 200 余页的论文至今仍是理解 Nix 设计意图最权威的一手材料，且可读性很高。

> **论文的核心论断**可以浓缩成一句话：把软件组件间的部署关系建模为纯函数式的、按内容寻址的不可变图，则部署的全部经典难题（依赖完整性、多版本、回滚、可复现、垃圾回收）都化为图上的平凡操作。

## 2.3 从论文到系统：设计决定的历史必然性

带着第 1 章的问题清单回看，Nix 的几个「怪设计」其实是上述模型的最直接推论：

**为什么是 `/nix/store/<哈希>-<名字>` 这样的路径？** 因为按内容寻址（content-addressing）要求路径编码身份。哈希由全部构建输入计算而来，路径本身就是「这个包是什么」的指纹（详见第 14、15 章）。Perl 时代（见 2.4 节）这个前缀一度写作 `/nix/store`，未曾改变。

**为什么要发明一门新语言？** 因为「描述构建物组合」需要一种惰性、纯函数式、擅长操作属性集的语言，而 2003 年候选（Scheme、Haskell）要么嵌入成本高、要么对非程序员不友好。Nix 语言刻意做小——没有类型系统、没有并发、没有 IO，只有表达式求值（第 6 章起详述）。

**为什么构建要隔离在沙箱、禁止网络？** 纯函数不能读参数之外的世界。允许构建过程联网读环境，等于允许函数偷读全局变量——输入不再是全部输入，哈希就失去了意义（第 16 章）。

**为什么升级=切换符号链接？** 不可变对象不能「被升级」，只能「被替换引用」。profile 指向新的 store 路径，旧路径原样保留，于是回滚天然存在（第 18 章）。

## 2.4 工程演进：从 Perl 原型到多实现时代

一个常被忽略的工程史实：Nix 包管理器的前 18 年主要用 **Perl** 写成（配合 C++ 的 libstore 用于哈希与签名等底层）。2003 年的原型就是 Perl 脚本；这套代码一直服役到 2020 年代。随后官方启动了渐进的 C++/现代化重写：Nix 2.x 系列（2.4 起）引入实验性的新命令行与 Flakes；2023 年后代码库持续向 C++ 迁移并引入 Rust 组件（如新的 nix-installer）。同一时期，社区出现了多个独立实现：

- **Lix**（2024）：由前 Nix 核心贡献者团队 fork 的 C++ 实现，聚焦错误信息质量与可用性；
- **Tvix**（TVL 社区，2022 年起）：用 Rust 从零实现的 Nix 兼容求值器与构建器；
- **Determinate Systems**（2021 年成立的公司）：以官方 Nix 为基础提供安装器、FlakeHub 与企业工具（第 3 章详述）。

这印证了 Nix 的「协议」属性：**store 布局、derivation 格式、Nix 语言语义构成了一组稳定接口**，接口之上可以有多个竞争实现。用户脚本与 nixpkgs 在不同实现间基本通用。

## 2.5 学术血脉：Nix 之前的先驱

Dolstra 在论文中诚实梳理了前人工作，了解它们能更准确地为 Nix 定位：

- **Depot/CASE 环境与 CMU 的 SPOG? 类系统**：早期多版本软件库思想（如 1990 年代的 Depot、Vesta）。Vesta（DEC 研究院）甚至也按派生哈希缓存构建结果，但未形成通用生态。
- **函数式语言生态**：Haskell 社区的包管理困境直接反哺了 Nix 设计——Nix 最早的重度用户就包括 Haskell 工具链构建者。
- **BSD ports 与 Gentoo**：源码驱动的可定制构建，但状态仍是全局可变的。
- **Plan 9 与 9P? 无关不展开；PVCS? 不写**——论文引文里最重要的对照其实是 **Debian apt** 与 **Red Hat RPM**：两者证明「集中仓库+依赖求解」可行，也暴露了「全局可变命名空间」的天花板。

Nix 的独创性在于把这些分散的思想（内容寻址、纯函数、惰性语言、构建隔离）第一次**组合成一个自洽、通用、可实际使用的系统**，并配上了可扩展的包集合（nixpkgs）。

## 2.6 人物与传承

- **Eelco Visser**（导师，1966-2023）：程序变换领域学者，Stratego/XT 与 Spoofax 的创造者。他为 Nix 提供了问题场与研究框架。他于 2023 年去世，NixOS 社区发文纪念——没有 Stratego/XT 的构建之痛，就没有 Nix。
- **Eelco Dolstra**：Nix 与 NixOS 的创始人，长期担任项目的技术灵魂，2010 年代供职于 Delft 理工大学并持续维护 Nix/Hydra；NixOS 基金会理事会成员。（其 2020 年代后期的角色变化与社区治理演进见第 3 章。）
- **Armijn Hemel**：乌得勒支的另一位学生，2006-2007 年在硕士论文中把 Nix 从「包管理器」推向「完整 GNU/Linux 发行版」，做出 NixOS 原型（第 22 章详述）。
- **Sander van der Burg**：Dolstra 的同门，把纯函数式部署思想扩展到分布式服务（Disnix），其论文同样值得一读。
- 以及后来成千上万的 nixpkgs 贡献者——这个没有正式雇员、全靠志愿者的仓库，如今是地球上最大的软件仓库之一。

## 2.7 本章小结

- Nix 诞生于乌得勒支大学构建 Stratego/XT 的真实痛点，而非抽象的学术空想。
- 2004 年 ICSE 论文确立了核心抽象：**软件部署 = 内存管理**；不可变、引用追踪、GC、内容寻址被引入部署领域。
- 2006 年 Dolstra 博士论文《The Purely Functional Software Deployment Model》给出完整模型；Nix 的每个「怪设计」都是纯函数式模型的直接推论。
- Nix 经历了 Perl 原型 → 现代 C++/Rust 的工程演进，并衍生出 Lix、Tvix、Determinate 等多实现，「协议化」的接口保证了生态兼容。
- Nix 站在 Vesta、Haskell 生态、apt/RPM 等先驱的肩膀上，其独创在于把已有思想组合成自洽的通用系统。
