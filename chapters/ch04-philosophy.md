# 第 4 章 声明式与纯函数式包管理思想

> **本章导读**：第 1 章说「Nix 把部署变纯」，第 2、3 章讲了这个想法的来龙去脉。本章正面拆解它：声明式与命令式的分野是什么；纯函数与引用透明放进构建场景意味着什么；不可变存储如何把「时间维度」引入文件系统；以及这套哲学的边界在哪里——它不解决什么问题。读懂本章，第 13-21 章的每个机制都会显得「理所当然」。

## 4.1 命令式与声明式：两种「安装」的世界观

对「我要在这台机器上装好 nginx」这个需求，两种世界观给出完全不同的答案：

**命令式（imperative）**——传统做法，安装是一连串改变世界的动作：

```bash
# Debian 世界：一串改变机器状态的命令
$ apt update
$ apt install -y nginx
$ sed -i 's/listen 80;/listen 8080;/' /etc/nginx/sites-enabled/default
$ systemctl restart nginx
```

机器的最终状态 = 初始状态 × 命令历史的累积。要复现它，你必须重放全部命令（且顺序、环境、时机都得一致）。`apt install` 执行两次与一次可能不同（版本滚动）；某条命令失败后的状态无人知晓——这就是第 1 章「配置漂移」的技术本质：**状态是命令的副作用，没有独立的存在形式**。

**声明式（declarative）**——Nix 的做法，安装是「陈述一个事实」：

```nix
# NixOS 世界：一份描述「机器应该是什么样」的配置
{
  services.nginx = {
    enable = true;
    virtualHosts."example.com".listen = [ { addr = "0.0.0.0"; port = 8080; } ];
  };
}
```

这份配置**就是**机器状态的完整定义：当前状态与它不符，就重建出新状态并切换过去；已经相符，什么都不做。不存在「装到一半」；不存在「哪条命令执行过了」的历史包袱——历史只存在于 git 与 NixOS 的 generation 机制里，而不存在于机器本身。

一个精确的对照表：

| 维度 | 命令式 | 声明式 |
|------|--------|--------|
| 状态存在于 | 机器的当前文件系统 + 命令历史 | 一份（可版本化的）配置 |
| 复现方式 | 重放命令 | 重新求值配置 |
| 幂等性 | 依赖工具实现 | 天然成立（同配置同结果） |
| 部署单位 | 一条条变更 | 整个系统闭包 |
| 回滚 | 反向命令（常常不存在） | 切回上一个 generation |
| 审计 | 翻 shell 历史 / 日志 | `git log` 配置仓库 |

需要强调：声明式不是 Nix 的专利——Ansible/Puppet/Kubernetes 也是声明式的。Nix 的独特之处在于**声明可以精确到字节**：它的求值结果是密码学哈希锚定的构建产物，而 Ansible 的「期望状态」最终仍要落到目标机上的 `apt`（命令式工具）去执行。声明式只有落到 Nix 的函数式构建模型上，才获得完全的可复现性。

## 4.2 纯函数与引用透明：构建的数学化

回忆第 1 章的抽象：`install = f(源码, 工具链, 依赖, 参数)`。函数式编程对「纯」有两条规定：

1. **引用透明（referential transparency）**：同样的输入，永远得到同样的输出——表达式可以用它的值替换而不改变程序含义；
2. **无副作用**：函数不读写参数之外的世界。

Nix 把构建过程放到这两条戒律下，逐条落实到机制：

| 纯函数的要求 | Nix 的机制 | 详见 |
|--------------|-----------|------|
| 输入必须全部显式 | 派生（derivation）记录完整输入清单：源码哈希、构建脚本、依赖路径、环境变量 | 第 13 章 |
| 输入相同 ⟹ 输出相同 | 输出路径 = 全部输入的哈希；已有路径直接复用（构建缓存） | 第 14、15 章 |
| 不许读外界 | 构建沙箱：私有 mount namespace、断网、受限环境变量 | 第 16 章 |
| 不许写外界 | 构建只能写入自己的输出目录 `/nix/store/<hash>-<name>` | 第 13、14 章 |
| 不许用「当前时间」等噪声 | 时间戳、随机数被视为输入的一部分；追求字节级可复现 | 第 16 章 |

其中最有电力的一步是**用哈希给输出命名**：`/nix/store/p7d...-hello-2.12.3`。路径本身就是输入的指纹，于是「引用透明」获得了文件系统层面的体现——你在任何地方看到这个路径，就知道它里面是什么、从何而来。传统系统的 `/usr/bin/hello` 是一个**变量**（内容随时间变化），`/nix/store/...-hello-2.12.3` 是一个**常量**。

## 4.3 不可变性：把时间维度装进文件系统

不可变（immutable）存储带来三个直接推论，每个都值得单独品味：

**1. 多版本共存是平凡的。** hello 2.12.1 与 2.12.3 是两个不同路径，各自完整、各自带依赖，共存不冲突。第 1 章的「问题一」在文件系统层面消失。

**2. 回滚是免费的。** 升级 = 新建路径 + 切换引用；回滚 = 把引用切回旧路径。旧路径没有被破坏，所以回滚永远可行——这与数据库的 MVCC、函数式数据结构「持久化」（persistent）同构。

**3. 「系统状态」可以是一个值。** 一台 NixOS 机器的当前状态，就是 `/nix/var/nix/profiles/system` 这个符号链接指向的 store 路径。比较两台机器是否一致 = 比较两个哈希。备份系统 = 备份一份配置 + 一份闭包清单。

```
        ┌─── profile → /nix/store/aaa...-system-2026A   ← 当前（generation 42）
/nix/store┤
        ├─── 旧 profile → /nix/store/bbb...-system-2025  ← generation 41（还在，可随时切回）
        └─── ...每个包、每个中间产物，全部按输入哈希永久躺在 store 里
```

不可变的代价是磁盘（第 19 章的 GC 解决）与「不能就地改文件」的心智转变（NixOS 用生成 /etc、声明式用户等方式补偿，第 26、30 章）。

## 4.4 惰性：描述全世界，只算你需要的

nixpkgs 描述了超过十万个包，但 `nix build nixpkgs#hello` 秒级完成求值——因为 Nix 语言是惰性的：**没被引用的包定义永远不会被求值**。这一点常被低估其重要性：

- 它让 nixpkgs 可以无限膨胀而不拖慢单个构建；
- 它让 NixOS 模块系统能表达出「配置之间互相依赖却不成环」的复杂拓扑（第 25 章）；
- 它是 `lib.fix` 自引用（第 7、11 章）合法性的前提。

用函数式编程的行话说：整个包集合是一张**按需展开的惰性图**（lazy graph），而不是一份要全部执行的清单。

## 4.5 闭包：依赖完整性的构造性证明

传统系统回答「这个程序依赖什么」靠扫描（`ldd`、`dpkg -s`、试运行）。Nix 的回答是构造性的：每个 store 对象**在创建时就声明了它引用的全部对象**（references），运行所需集合 = 引用关系的传递闭包（closure）。

- 完整性不再是「希望没漏掉什么」，而是**数学事实**（第 17 章）；
- 部署一个程序 = 复制它的闭包，不多不少；
- 这也解释了为什么 Nix 能把整个操作系统当作「一个包」来构建与切换（第 23 章）。

## 4.6 函数式思想的整体图景

把本章概念串成一张图：

```
              声明式配置（configuration.nix / flake.nix）
                        │  求值（Nix 语言，惰性、纯）
                        ▼
              派生图（derivations：构建的函数）
                        │  构建（沙箱内，纯函数式执行）
                        ▼
        /nix/store/<输入哈希>-<名字>（不可变对象 + 引用关系）
                        │  组装（profile / system path）
                        ▼
        当前系统（一个符号链接指向的闭包；generation 可切换）
```

自上而下：描述（what）→ 配方（how，可哈希）→ 产物（不可变）→ 状态（可切换）。每一层的输出都是下一层的纯输入。第 22-28 章会看到 NixOS 如何把最顶层的「整台机器」也纳入这套流水线。

## 4.7 哲学的边界：Nix 不解决什么

诚实的工程讨论必须画清边界：

1. **不解决运行期状态**。数据库里的数据、`/var/lib` 的文件、用户的 home——这些是「数据」，不是「软件」，Nix 有意不管（管理思想见第 30 章）。
2. **不自动保证字节级可复现**。哈希锁定的是**输入**；若构建脚本嵌入了时间戳，两次构建的输出路径相同（缓存命中）但字节可以不同。字节级可复现需要额外的纪律与工具（第 16 章）。
3. **不处理非代码的「环境噪声」**。内核版本、硬件、时区可能影响程序行为，它们不在 Nix 的哈希域内。
4. **安全模型信任上游**。Nix 保证「依赖图完整」，不保证「上游代码无害」——供应链安全的真正防线在别处（签名、审计、最小化）。
5. **有学习曲线与迁移成本**。对一次性脚本、重度依赖系统全局状态的软件（某些闭源驱动、需要 patch 系统调用的工具），Nix 化的成本可能超过收益。

## 4.8 本章小结

- 声明式让「状态」获得独立于命令历史的存在形式；Nix 把声明式推进到「哈希锚定的字节级」。
- 纯函数的两大戒律（引用透明、无副作用）被逐条落实为机制：派生、store 哈希、沙箱、私有输出目录。
- 不可变性带来多版本共存、免费回滚与「系统状态是一个值」；惰性让巨型包集合按需展开。
- 闭包把依赖完整性从「扫描结果」升级为「构造性数学事实」。
- 边界同样重要：运行期状态、字节级复现、环境噪声、上游可信度不在 Nix 的解决域内。
